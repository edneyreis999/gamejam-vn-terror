# MZ Tests and Their Upkeep

Read when writing, running, reviewing, or pruning automated tests for an MZ game, including a final-verification purge of the tests a delivery added. Apply these practices to the game's actual test setup and active plugins.

- **Test what the game loads.** A test reads only what the shipped game uses: no disabled plugin, unused asset, or editor-only file. When the published build is pruned, run the suite against that pruned build so a test cannot pass on a file the player never gets.
- **Compare keys, not translated text.** Where text lives in a localization file and events hold only a key, tests assert the key or the value read from that file. `$gameMessage.choices()` holds the raw key, not the displayed text.
- **Protect observable game contracts:** save and load, death, progress and event order, as well as functional presentation such as readable dialogue, visible controls and an advance indicator that fits the text box. Subjective color or styling preference alone does not justify a regression test. Distinct authored prose can produce different native geometry despite identical event-command structure; a data comparison or traversal without a geometry assertion does not replace required rendered variants.
- **Infrastructure proof is not game proof.** A test that only shows the test server or browser starts protects nothing; the whole suite already fails if either breaks.
- **Playwright E2E:** use [Game Playwright Best Practices](../../game-playwright-best-practices/SKILL.md) for test units, lifecycle, evidence, and stability. Read [Playwright E2E for MZ](playwright-e2e.md) for the engine's scenes, input, windows, and storage when writing, reviewing, or debugging browser journeys.
- **Parallel execution requires isolation.** When tests bind one fixed port or share mutable game files, save storage, browser profiles, temporary paths or evidence destinations, run them serially unless the harness proves per-worker isolation. Account for the actual number of browsers each case opens when limiting concurrency. Keep renderer and runtime settings comparable, and verify teardown of processes owned by the run; never stop an unrelated server merely to free its port. Parallelism does not justify changing assertions, required variants or timeouts.
- **Build the shared execution capability at its first consumer.** Use [game-test-infrastructure](../../game-test-infrastructure/SKILL.md) for the general creation or repair procedure when a capability is missing or defective. Read [runtime test execution](runtime-test-execution.md) for MZ fixture preparation and executor constraints, including slow-test parallelism. Keep the executor in the project, reuse it across specs, and consume the root slow-test configuration. A finished queue or exit code alone does not prove every selected case ran.
- **A red test is not a deletion reason.** Find the cause. If the game is right and the test is stale, repair its observation while preserving the contracted guarantee.
