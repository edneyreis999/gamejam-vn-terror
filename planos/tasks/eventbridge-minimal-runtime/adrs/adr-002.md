# ADR-002 — Direct Common Event calls and default image loading

Status: accepted by user direction on 2026-09-12, after review round 01. This amends the approved, unimplemented spec; it does not authorize runtime execution or claim verification.

Subsequent scope addition: [ADR-003](adr-003.md) includes CoreEngine System: Load Images for every tavern image. It supersedes the tavern portion of the preload exclusion below; the default loading/error lifecycle and absence of a project readiness barrier remain in force.

## Context

[Review round 01](../review-01.md) identified duplicate ownership between configurable content references and native Common Event calls, and an unspecified replacement for Bridge's image-readiness hooks. The assistant proposed adding content dispatch to Bridge and an image-wait command to Presentation. The user instead directed direct native calls and investigation of native/provider loading, accepting RPG Maker's default behavior if no native solution exists.

## Decision

The Gorvak event uses native choices and, when the player chooses Conversar, native Chamar evento comum to run the conversation. Apply that direct event-owned routing to the other narrative units. The selected Common Event in the native call is the content association; do not copy it into ConfigureHero/Encounter/Scene or add a Bridge dispatch command. Shared native Common Events may contain the interaction and its branches. The named map event must expose the actual authored path used by the interaction.

Keep public identity/configuration data in editor fields accessible through Configuração do jogo. Narrative routing and image selection belong to their native event commands. CampaignRules still owns existing semantic passage identities, eligibility and progression; events query needed facts and explicitly report actual campaign reading completion through Bridge. Conversations remain observational. Bridge does not locate or execute their text.

For image loading, use MZ and the installed providers as supplied. Do not add a project image-wait command, bitmap polling, loading interception or an immediate-Retry guarantee. If their normal behavior delays an image or surfaces an error later, retain that behavior. Native Retry remains available where the engine/provider supplies it. Required production assets must still exist. Preload remains the separate known issue and no preload setting or command is added by this amendment.

## Native capability investigation

- The installed MZ is 1.10.0. Native `command117` directly executes the selected Common Event list (`js/rmmz_objects.js`). No Bridge resolution is required for that call.
- CoreEngine 1.90 offers `SystemLoadImages`, with editor file selectors. Inspection of its installed command callback established that it calls `ImageManager.loadBitmap` for the selected files and returns; it does not set an interpreter wait or await readiness. Its boot Image Loading parameters also concern preload. The [provider documentation](https://www.yanfly.moe/wiki/Core_Engine_VisuStella_MZ#System_Plugin_Commands) describes the command as loading images ahead of use, and [Image Loading](https://www.yanfly.moe/wiki/Core_Engine_VisuStella_MZ#Image_Loading) explains the asynchronous/cache behavior. These features are not a scene-local readiness-and-Retry operation.
- Native Show Picture has no bitmap-ready wait field. Wait for Completion on Move/Tint Picture waits for that operation's duration, as documented in the [MZ picture commands](https://rpgmakerofficial.com/product/MZ_help-en/01_10_08.html). VNPictureBusts' documented animation wait does not provide an image-loader wait either.
- The engine does have the internal `setWaitMode("image")` API: `Game_Interpreter.updateWaitMode` checks the whole ImageManager cache (`js/rmmz_objects.js:9638–9640`). Calling it from an event requires Script; it neither selects nor initiates loading of a particular file. It is not a ready editor command for the specified operation. Wrapping this API or combining it with preload would introduce the script/loading recipe the user wants to avoid in this increment.
- Native `Scene_Base.isReady` calls `ImageManager.isReady` before scene start; that manager raises native LoadError/Retry. The removed Bridge update hook also checked readiness during an already-running map. This amendment accepts the engine/provider lifecycle instead of reproducing that extra guarantee.

No ready native editor operation meeting the former explicit per-image readiness and immediate error requirement was identified without adding a Script recipe or preload. Given the no-JavaScript authoring scope and the separate preload issue, the user-authorized default-behavior fallback applies. This is not a claim that MZ lacks an internal readiness API. The conclusion is based on source and documentation inspection, not a cold-cache or missing-file playtest.

## Supersession and verification

This supersedes the spec's duplicate Configure* content references, ConfigureScene command proposal, and RQ-009's requirement for a project-supplied explicit image wait. It resolves F-001/F-002 through the user's simpler direction, rather than approving the assistant's two proposed commands. ADR-001 otherwise remains in force.

V-003/S03 must edit the actual native Common Event call and verify the content reached from that path. V-008/S06 must observe ordinary cold, delayed and failed loading, exercise Retry where supplied, and distinguish native behavior from migration defects. They must not fail merely because the removed custom wait/Retry guarantee is absent. Implementation, runtime observations and human acceptance remain pending.
